كيف تبني لغتك البرمجية
هذا الكتاب محاولة لسدّ فراغ واضح في المكتبة العربية: لا يوجد تقريبًا كتاب تعليمي منهجي يشرح كيف تُبنى لغة برمجة جديدة خطوةً بخطوة، بلغة عربية واضحة، مع أمثلة عملية كاملة.

سنمشي معًا من الصفر، وكأنك لم تبنِ من قبل أي مفسِّر (Interpreter) أو مُصرِّف (Compiler)، لكن لديك خبرة مع البرمجة عمومًا (مثلاً: Python أو JavaScript أو غيرها).

لماذا قد تريد بناء لغة برمجة؟
هناك أسباب كثيرة تدفع مطوّرًا لبناء لغة خاصة به، منها:

لغة مجالية (DSL) لحل مشكلة معيّنة (وصف قواعد عمل، وصف سيناريوهات، قوانين…)
لغة تعليمية لتعليم البرمجة أو المنطق أو الرياضيات بطريقة بسيطة
لغة تجريبية لتجربة أفكار لغوية جديدة (أنماط كتابة، أنواع بيانات، منطق ضبابي، منطق احتمالي…)
أو حتى لغة إنتاجية متكاملة، وهذا عادةً يأتي بعد سنوات من التجريب والتطوير.

هذا الكتاب لا يَعِدُك بأن تخرج في نهايته بلغة جاهزة للمنافسة مع C++ أو Python، لكنه يَعِدُك أن تخرج بـ فهم عميق للخطوات الأساسية، وأن تمتلك أدوات عقلية وعملية تؤهّلك لمشاريع أكبر لاحقًا.

كيف تكتب مفسِّرًا (Interpreter) ينفّذ الـ AST مباشرة؟

1. إضافة مفهوم «الكتلة» للمفسّر

python نسخ
def استخراج_كتلة(الأسطر, الفهرس_الحالي):
    كود_الكتلة = []
    مستوى = 0
    i = الفهرس_الحالي
    # نتوقع أن السطر الحالي هو السطر الذي يحوي '{'
    while i < len(الأسطر):
        سطر = الأسطر[i].strip()
        if '{' in سطر:
            مستوى += 1
        if '}' in سطر:
            مستوى -= 1
            if مستوى == 0:
                return كود_الكتلة, i  # i هو آخر سطر في الكتلة
        if مستوى > 0 and not سطر.endswith('{') and سطر != '}':
            كود_الكتلة.append(سطر)
        i += 1
    raise ValueError("أقواس الكتلة غير متطابقة")

عندما يعود المستوى إلى 0 نكون قد وصلنا إلى نهاية الكتلة
بذلك يمكننا إعادة استخدام هذه الدالة لكل من الشرط والحلقة.

import re

class مفسر_بسيط:
    # ... (بقية التعريف كما في الفصل السابق)

    def تفسير(self, الكود: str) -> None:
        الأسطر = الكود.split('\n')
        i = 0
        while i < len(الأسطر):
            سطر = الأسطر[i].strip()
            if not سطر or سطر.startswith('#'):
                i += 1
                continue

            if سطر.startswith('إذا'):
                i = self.معالجة_الشرط(الأسطر, i)
            elif سطر.startswith('كرر'):
                i = self.معالجة_الحلقة(الأسطر, i)
            else:
                self.معالجة_السطر(سطر)
                i += 1
ثم نضيف دالّة الشرط:

python نسخ
    def معالجة_الشرط(self, الأسطر, موضع):
        سطر = الأسطر[موضع]
        match = re.search(r'إذا\s*\((.*)\)', سطر)
        if not match:
            raise ValueError("صيغة إذا غير صحيحة")
        شرط = match.group(1)

        # جسم if
        # نتوقع أن السطر التالي يحوي '{'
        كتلة_if, نهاية_if = استخراج_كتلة(الأسطر, موضع + 1)

        # هل يوجد وإلا بعدها؟
        كتلة_else = None
        موضع_بعد_if = نهاية_if + 1
        if موضع_بعد_if < len(الأسطر):
            سطر_بعد = الأسطر[موضع_بعد_if].strip()
            if سطر_بعد.startswith('وإلا'):
                كتلة_else, نهاية_else = استخراج_كتلة(الأسطر, موضع_بعد_if + 1)
                موضع_بعد_if = نهاية_else + 1

        if self.تقييم_شرط(شرط):
            self.تفسير('\n'.join(كتلة_if))
        elif كتلة_else is not None:
            self.تفسير('\n'.join(كتلة_else))

        return موضع_بعد_if
هنا استخدمنا دالة تقييم_شرط يمكن تعريفها ببساطة عبر إعادة استخدام تقييم_تعبير مع بعض الضوابط:

python نسخ
    def تقييم_شرط(self, شرط: str) -> bool:
        نتيجة = self.تقييم_تعبير(شرط)
        return bool(نتيجة)

    def معالجة_الحلقة(self, الأسطر, موضع):
        سطر = الأسطر[موضع]
        match = re.search(r'كرر\s*\((.*)\)', سطر)
        if not match:
            raise ValueError("صيغة كرر غير صحيحة")
        محتوى = match.group(1)
        أجزاء = [ج.strip() for ج in محتوى.split('؛')]
        تهيئة, شرط, تحديث = أجزاء

        # تنفيذ التهيئة مرة واحدة
        self.معالجة_السطر(تهيئة)

        # جسم الحلقة
        كتلة, نهاية = استخراج_كتلة(الأسطر, موضع + 1)
        جسم = '\n'.join(كتلة)

        while self.تقييم_شرط(شرط):
            self.تفسير(جسم)
            self.معالجة_السطر(تحديث)

        return نهاية + 1

في الفصول التالية سنبدأ في تنظيف هذا المفسّر وجعله أقرب إلى بناء كلاسيكي (Lexer/Parser)، ثم نربط الأفكار بما هو أعمق كما في لغة البيان.

تجربة شرط بدون «إلا»
اكتب برنامجًا يستخدم إذا فقط بدون كتلة وإلا، مثل:

تجربة حلقات مختلفة
اكتب عدة أمثلة لحلقات كرر:

هذه التمارين ليست لإجبارك على تصميم كامل للّغة، بل لتعتاد على التفكير في: ماذا يحدث لو غيّرت سطرًا واحدًا في المفسّر؟ وكيف تنعكس هذه التغييرات على سلوك اللغة.

الفصل الرابع: من مفسّر يعتمد على الأسطر إلى Lexer/Parser للغة «بسيطة»
في الفصول السابقة بنينا لغة «بسيطة» ومفسّرًا تعليميًا لها يعتمد مباشرة على قراءة الأسطر وتخمين نوع كل سطر (إسناد، شرط، حلقة، طباعة...).

هذا الأسلوب ممتاز للتعلّم، لكنه:

يصبح صعبًا عند زيادة تعقيد اللغة
يجعل التعامل مع الأخطاء أصعب
يقيّدك بشكل معيّن لكتابة الكود (سطر = أمر واحد تقريبًا)
في هذا الفصل سنقترب خطوة من الشكل الكلاسيكي لبناء اللغات:

نفصل بين تحويل النص إلى رموز (Lexing)
ثم تحويل الرموز إلى بنية شجرية (Parsing / AST)
لن نعيد بناء كل شيء دفعة واحدة، بل سنعرّف نموذجًا مبسطًا جدًا يكفي لفهم الفكرة.

1. ما هي الـ Token؟
بدل أن نتعامل مع النص كسلسلة أحرف، نقسّمه إلى رموز (Tokens)، مثل:

اسم متغير: س, مجموع
رقم: 10, 3
كلمة مفتاحية: إذا, وإلا, كرر, اطبع
رمز: =, +, -, (, ), {, }
في Python يمكننا تمثيل الرمز هكذا:

python نسخ
from dataclasses import dataclass
from enum import Enum, auto

class TokenType(Enum):
    IDENT = auto()   # اسم متغير أو دالة
    NUMBER = auto()
    STRING = auto()
    KEYWORD = auto()
    SYMBOL = auto()
    EOF = auto()     # نهاية الملف

@dataclass
class Token:
    type: TokenType
    value: str
    line: int
    col: int
بهذا أصبح لكل جزء في النص «هوية» واضحة ومعلومة موقعه (سطر/عمود) لرسائل الخطأ.

2. بناء Lexer بسيط للغة «بسيطة»
الـ Lexer يأخذ النص الخام ويعيد قائمة من الرموز:

python نسخ
class Lexer:
    KEYWORDS = {"إذا", "وإلا", "كرر", "اطبع"}

    def __init__(self, source: str):
        self.source = source
        self.pos = 0
        self.line = 1
        self.col = 1

    def tokenize(self):
        tokens = []
        while self.pos < len(self.source):
            ch = self.source[self.pos]
            if ch.isspace():
                self._consume_whitespace()
            elif ch.isalpha() or ch == "_":
                tokens.append(self._identifier_or_keyword())
            elif ch.isdigit():
                tokens.append(self._number())
            elif ch in '"'":
                tokens.append(self._string())
            else:
                tokens.append(Token(TokenType.SYMBOL, ch, self.line, self.col))
                self._advance()
        tokens.append(Token(TokenType.EOF, "", self.line, self.col))
        return tokens
والدوال المساعدة يمكن أن تكون شيئًا من هذا النوع:

python نسخ
    def _advance(self):
        ch = self.source[self.pos]
        self.pos += 1
        self.col += 1
        if ch == "\n":
            self.line += 1
            self.col = 1

    def _consume_whitespace(self):
        while self.pos < len(self.source) and self.source[self.pos].isspace():
            self._advance()

    def _identifier_or_keyword(self):
        start = self.pos
        while self.pos < len(self.source) and (self.source[self.pos].isalpha() or self.source[self.pos] == "_"):
            self._advance()
        text = self.source[start:self.pos]
        ttype = TokenType.KEYWORD if text in self.KEYWORDS else TokenType.IDENT
        return Token(ttype, text, self.line, self.col)

    def _number(self):
        start = self.pos
        while self.pos < len(self.source) and self.source[self.pos].isdigit():
            self._advance()
        text = self.source[start:self.pos]
        return Token(TokenType.NUMBER, text, self.line, self.col)
ملاحظة: يمكن لاحقًا دعم الأرقام العشرية، والتعليقات، وأنواع رموز أخرى، لكن هذه النواة تكفي لتجاربنا الأولى.

3. من الرموز إلى شجرة تركيب (AST) بسيطة
الآن بعد أن أصبح لدينا رموز، نريد تحويلها إلى عُقد (Nodes) تمثّل معنى البرنامج، مثل:

تعليمة إسناد: Assign(name="س", expr=...)
أمر طباعة: Print(expr=...)
بشكل مبدئي يمكن أن نعرّف:

python نسخ
class Assign:
    def __init__(self, name, expr_tokens):
        self.name = name
        self.expr_tokens = expr_tokens  # سنبقي التعبير كقائمة رموز في هذه المرحلة

class Print:
    def __init__(self, expr_tokens):
        self.expr_tokens = expr_tokens
ثم نكتب محلّلًا صغيرًا لسطر واحد من نوع الإسناد أو الطباعة:

python نسخ
def parse_simple_line(tokens):
    # مثال مبسط جدًا: إما "اسم = تعبير" أو "اطبع(تعبير)"
    if tokens[0].type == TokenType.KEYWORD and tokens[0].value == "اطبع":
        # نتجاهل التفاصيل هنا ونمرر ما بداخل الأقواس كـ expr_tokens
        return Print(tokens[1:-1])
    elif tokens[0].type == TokenType.IDENT and tokens[1].value == "=":
        return Assign(tokens[0].value, tokens[2:-1])
    else:
        raise SyntaxError("سطر غير معروف الصيغة")
هذا المثال ليس مفسّرًا كاملاً، لكنه يوضّح الفكرة الجوهرية:

النص → Tokens (Lexer)
Tokens → AST (Parser)
AST → تنفيذ (Interpreter)
في الفصول القادمة سنستفيد من هذه البنية لتنظيف مفسّر «بسيطة»، وتحسين رسائل الخطأ، ثم إضافة ميزات لغوية جديدة.

اكتب نصًا قصيرًا للّغة «بسيطة» (3–5 أسطر)، ثم:

تجربة تعديل قائمة الكلمات المفتاحية

اكتب سطرًا يستخدم هذه الكلمة.

تأكّد من أن الـ Lexer يصنّفها كـ KEYWORD وليس IDENT.

أزِلها من القائمة، وراقب الفرق في ناتج الـ Tokens.

تغيير بسيط في شكل AST
عدّل تعريف Assign أو Print بحيث تضيف حقلًا جديدًا (مثلاً: رقم السطر الذي جاءت منه التعليمة)، ثم عدّل parse_simple_line لتمرير هذه المعلومة. الهدف:

أن ترى كيف يرتبط تصميم AST بالمعلومات التي تحتاجها لاحقًا في المفسّر أو رسائل الخطأ.

لا تحاول في هذه المرحلة بناء Parser كامل لجميع تراكيب «بسيطة»؛ يكفي أن تتقن الحركة بين المراحل الثلاث: نص → Tokens → AST، وتفهم كيف يمكن تطوير كل مرحلة عند الحاجة.

الفصل الخامس: توسيع «بسيطة» بالأنواع والدوال ورسائل الخطأ
بعد أن رأينا كيف نحسّن بنية المفسّر باستخدام Lexer/Parser مبسّطين، حان الوقت لطرح سؤال عملي:

كيف نجعل لغة «بسيطة» أكثر فائدة قليلًا دون أن نفقد بساطتها؟

سنركّز هنا على ثلاثة محاور:

لن نكتب كل التفاصيل البرمجية في هذا الفصل، بل نضع تصميمًا واضحًا وخطوطًا عريضة للكود.

حتى الآن تعاملنا مع:

أعداد صحيحة (int)
سلاسل نصية (string) بطريقة مبسّطة
يمكن أن نوسّع هذا إلى مجموعة صغيرة من الأنواع:

String (نص)
Bool (صحيح/خطأ) لنتيجة المقارنات

في المفسّر يمكننا تمثيل القيمة مع نوعها، مثلًا:

3. رسائل خطأ مفهومة
لأن لدينا الآن Token تحتوي على (السطر، العمود)، يمكن أن تكون رسائل الخطأ:

تشير إلى الموضع بدقة
تخبر المستخدم ما الذي توقّعه المفسّر وما الذي وجده

في الكود هذا يعني:

تمرير كائن Token أو معلوماته إلى الإستثناء
تعريف استثناءات خاصة بالمفسّر، مثل:
python نسخ
class SimpleLangError(Exception):
    pass

class SimpleSyntaxError(SimpleLangError):
    def __init__(self, message, token):
        self.message = message
        self.token = token
        super().__init__(self.__str__())

    def __str__(self):
        return f"[{self.token.line}:{self.token.col}] {self.message}"
ثم داخل الـ Parser:

اختر مجموعة صغيرة من الميزات (مثلاً: الدوال بدون ارجع + نوع Bool + رسائل خطأ)
نفّذها خطوة بخطوة في المفسّر

بعد أن تتقن هذه المرحلة، ستكون مستعدًا للانتقال من لغة تعليمية صغيرة إلى أفكار أعمق بكثير، كما في اللغات الهجينة والمنطقية مثل «البيان».

بعد أن صمّمنا لغة «بسيطة» وبنينا لها مفسّرًا تعليميًا، وحسّنا البنية باستخدام Lexer/Parser مبسّطين، حان الآن وقت تجميع هذه الأفكار في مشروع صغير متكامل يمكن تشغيله، ثم النظر كيف يمكن أن تتطوّر نفس الأفكار نحو لغة أعمق مثل «البيان».

from simple_lang.lexer import Lexer
from simple_lang.parser import Parser
from simple_lang.interpreter import Interpreter

def run_file(path: str):
    with open(path, 'r', encoding='utf-8') as f:
        source = f.read()
    tokens = Lexer(source).tokenize()
    ast = Parser(tokens).parse_program()
    interp = Interpreter()
    interp.execute(ast)

if __name__ == "__main__":

3. من «بسيطة» إلى «البيان»: ما الذي يتغيّر؟
على مستوى الأفكار، كثير مما فعلناه في «بسيطة» يشبه ما يحدث في لغات أكبر:

التقسيم إلى مراحل:

Lexer
Parser
Interpreter / Compiler
بنية داخلية لتمثيل البرنامج (AST أو ما يشبهها)

بيئات (Environments) للمتغيرات والدوال والأنواع.

ما الذي تضيفه لغة مثل «البيان» فوق هذا؟

نظام كيانات وحالات: كيان (Entity) يمتلك حالات (States) وضبابية واحتمالات
منطق (Logic) واستعلامات: حقائق، قواعد، استعلامات، وربما احتمالات
تشابه ودلالة: معاني، معلومات، أنطولوجيات، ومكتبات تشابه ومترادفات
تكامل مع الذكاء الاصطناعي: وحدات قادرة على استخدام نماذج تعلم عميق أو إحصائية
من منظور "مراحل اللغة"، تظل الفكرة العامة:

هناك نص → يتحول إلى رموز/عقد → يتحول إلى تمثيل داخلي غني
هناك «مفسّر» أو «محرك» يأخذ هذا التمثيل ويقوم بعمل معقّد (استنتاج، بحث، محاكاة، ...)
الفرق أن البيان اخترع عالمًا داخليًا أغنى بكثير من مجرد متغيرات وأعداد وحلقات.

4. كيف تستفيد من «بسيطة» في فهم «البيان»؟
عندما تقرأ لاحقًا عن أجزاء من مترجم البيان (الـ lexer, parser, ast, interpreter):

تذكّر أن كل جزء منها له قرين أبسط في «بسيطة»:
جدول المتغيرات في «بسيطة» يشبه جزئيًا بيئات الكيانات أو المتغيرات في البيان
دوال evaluate_expr في «بسيطة» تشبه طرق تقييم التعبيرات في البيان (لكن البيان يدعم أنواعًا ومنطقًا أوسع)
بنية المفسّر التي تمشي على AST تشبه ما يفعله محرك الكيانات أو المنطق في البيان
بهذا يصبح الانتقال من لغة تعليمية صغيرة إلى لغة هجينة متقدّمة انتقالًا طبيعيًا: نفس المراحل، لكن:

أنواع أكثر
بنى بيانات أعمق
محرك منطق/كيانات/دلالات بدلاً من مجرد تعابير عددية ونصوص
5. الخطوة العملية التالية للقارئ
بعد هذا الفصل، إذا أردت أن تجعل ما قرأته جزءًا من خبرتك العملية:

نفّذ مشروع «بسيطة» كما هو موصوف (أو قريبًا منه) في مجلد منفصل.

جرّب إضافة ميزة صغيرة بنفسك (نوع جديد، دالة، بنية تحكم).

انتقل بعدها لقراءة أجزاء من مترجم البيان مع مقارنة كل جزء بما يقابله في «بسيطة».

بهذا الأسلوب تصبح قراءة كود لغة حقيقية (مثل البيان) تدريبًا مريحًا أكثر من كونها صدمة لأول مرة.

الفصل السابع: تصميم بناء الجملة للغات عربية – دروس من "بسيطة" والبيان
إلى هنا كنّا نتعامل مع "بسيطة" كلغة تعليمية يمكن كتابتها بأي كلمات؛ الآن نناقش جانبًا خاصًا: كيف نصمّم بناء الجملة (Syntax) للغات عربية؟ وما الذي يمكن أن نتعلمه من تجارب مثل "بسيطة" والبيان.

هذا الفصل نظري/تصميمي أكثر، مع أمثلة قصيرة.

1. تحديات خاصة باللغات العربية
هناك تحديات عملية تظهر بمجرد أن تقرّر أن تكون لغتك "عربية الوجه":

اتجاه الكتابة (يمين → يسار) في حين أن معظم الأدوات والمحررات والمكتبات تفترض أن الكود يكتب من اليسار إلى اليمين.

المزج بين العربية واللاتينية:
كلمات مفتاحية عربية (إذا, كرر, كيان, استعلام)
أسماء دوال/مكتبات لاتينية (math, similarity, print)
الأرقام والرموز:
هل تستخدم الأرقام العربية الغربية (0–9) أم الأرقام العربية الشرقية (٠–٩)؟
هل تستعمل نفس الرموز +, -, *, = أم تبحث عن بدائل؟
القراءة البشرية vs سهولة التنفيذ:
أحيانًا ما هو أجمل للعين العربية أصعب في التنفيذ (أو العكس).

البيان اختار حلولًا عملية:

دعم كلمات عربية مع الحفاظ على الرموز والأرقام اللاتينية القياسية.

دعم صيغة ثنائية اللغة (مثلاً: hybrid و هجين، query و استعلام).

2. مبادئ تصميم لبناء جملة عربي
يمكن تلخيص عدد من المبادئ العامة:

الاتساق:

إن اخترت كلمات عربية للمتحكمات (إذا, وإلا, كرر)، فحافظ عليها في كل مكان.

تجنّب خلط if في مكان وإذا في موضع آخر لنفس المعنى داخل نفس اللغة.

الوضوح على حساب الزخرفة:

اختيار استعلام أفضل من تعبير طويل وغامض.

في البيان مثلًا: كيان, حالة, استعلام تعطي إحساسًا طبيعيًا لما يجري.

الاقتراب من أنماط مألوفة:

بناء جملة يشبه ما اعتاده المبرمجون يساعد على الانتشار.

مثلاً، "بسيطة" استخدمت بنية شبيهة بـ C/Java في الحلقات، لكن بألفاظ عربية.

إتاحة مسار ثنائي اللغة:

السماح بشكل عربي وآخر إنجليزي لنفس الكلمة المفتاحية (كما في البيان) يساعد في الانتقال التدريجي.

3. من "بسيطة" إلى نحو عربي أوضح
لو أردنا جعل "بسيطة" عربية أكثر بشكل ممنهج، يمكننا:

استبدال if بـ إذا, وelse بـ إلا أو وإلا، وwhile/for بـ كرر.

الحفاظ على الرموز +, -, *, = كما هي لتجنّب تعقيد lexer بلا داعٍ.

اختيار أسماء دوال عربية قدر الإمكان (اطبع, مربع, مجموع).

مثال تخيلي لامتداد "بسيطة" نحو منطق أقرب للبيان:

إضافة كتلة منطقية بسيطة:
text نسخ
منطق {
  حقيقة أب("أحمد", "سعيد").

  قاعدة جد(?X, ?Z) :- أب(?X, ?Y), أب(?Y, ?Z).

  استعلام جد(?جد, ?حفيد).

}
هذه ليست لغة البيان، لكنها توضح كيف يمكن أن:

تستخدم كلمات عربية (حقيقة, قاعدة, استعلام).

تحتفظ ببناء جملة قريب من Prolog/منطق البيان.

4. دروس عملية من تصميم البيان
من تجربة البيان يمكن استخلاص عدد من الدروس المفيدة عند تصميم لغة عربية:

ثنائية الكلمات المفتاحية:

دعم شكلين للكلمة المفتاحية نفسها (عربي/إنجليزي) يسهل دمج أكواد قديمة وجديدة.

مثال: hybrid / هجين, fact / حقيقة, rule / قاعدة, query / استعلام.

عدم التضحية ببنية المترجم لأجل جمالية سطحية:

المترجم ما زال يتعامل مع Tokens وأنواع ثابتة؛ الاختلاف فقط في النصوص التي تُترجم إلى تلك الأنواع.

هذا يعفيك من إعادة بناء parser لكل شكل لغوي جديد، ما دمت تحافظ على نفس AST.

استخدام العربية حيث تضيف معنى:

البيان لا يترجم فقط الكلمات المفتاحية، بل يعرّف طبقات دلالية: معنى, معلومة, معرفة_متطورة, أنطولوجيا.

هذه المصطلحات ليست مجرد أسماء متغيرات جميلة، بل كيانات مفهومية في اللغة نفسها.

التحكم في العمق:

يمكن أن تبدأ بلغات تعليمية مثل "بسيطة" ثم تضيف تدريجيًا:
مفاهيم كيانات.

طبقات منطق.

طبقات احتمالية وضبابية.

5. نصائح ختامية لمن يصمم لغة عربية
ابدأ بنواة صغيرة جدًا (مثل "بسيطة")، ثم أضف العربية على مراحل.

صمّم أولًا الهيكل الداخلي (Tokens, AST, Interpreter)، ثم فكّر في أسماء عربية تناسبه.

اقرأ لغات أخرى الهامشية أو التجريبية (مثل لغات DSL في مجالات ضيقة) لتأخذ أفكارًا عن البناء، ثم عربها.

انظر إلى البيان لا كشيء يجب نسخه، بل كمثال على أن اللغة العربية قادرة على التعبير عن مفاهيم برمجية ومنطقية متقدّمة حين تُصمّم بعناية.

بهذا الفصل نكون قد وضعنا إطارًا فكريًا لتصميم نحو عربي. في الفصول اللاحقة (أو في وثائق منفصلة) يمكن أن نقترب أكثر من تفاصيل مترجم البيان نفسه، ونربط بين مفاهيم هذا الكتاب وبين ملفات lexer/parser/ast الحقيقية.

الفصل الثامن: لغة منطق عربية مصغّرة – من الحقائق إلى الاستنتاج
في هذا الفصل ننتقل من لغة «بسيطة» الإمبراطورية (أوامر، حلقات، دوال) إلى لغة منطق عربية مصغّرة تشبه فكرة Prolog، لكن بحجم وبساطة يناسبان كتابًا تعليميًّا.

لن نبني Prolog كاملة، بل نواة صغيرة تدعم ثلاث لبنات:

حقيقة: معلومة ثابتة
قاعدة: نمط استنتاجي يبني معلومات جديدة من حقائق أخرى
استعلام: سؤال نوجّهه إلى قاعدة المعارف
1. تصميم بناء الجملة (Syntax)
نقترح شكلاً عربيًّا بسيطًا:

text نسخ
منطق {
  حقيقة أب("أحمد", "سعيد").

  حقيقة أب("سعيد", "ليلى").

  قاعدة جد(?X, ?Z) :- أب(?X, ?Y), أب(?Y, ?Z).

  استعلام جد(?جد, ?حفيد).

}
الكتلة منطق { ... } تضم الحقائق والقواعد والاستعلامات.

المعرفات مثل أب, جد هي أسماء علاقات (Predicates).

المتغيرات نميّزها بعلامة ? قبل الاسم: ?X, ?Y, ?جد.

الفاصلة , تعني «و» داخل جسم القاعدة.

الرمز :- يربط رأس القاعدة بجسمها (كما في Prolog).

هذا التصميم قريب من عائلة لغات المنطق، لكنه يستخدم ألفاظًا عربية واضحة: حقيقة/قاعدة/استعلام.

2. تمثيل البيانات في المفسّر
قبل التفكير في الـ Lexer/Parser، من المفيد أن نضع نموذجًا بسيطًا لما نريد تخزينه في الذاكرة:

python نسخ
class Fact:
    def __init__(self, name, args):
        self.name = name      # مثل "أب"
        self.args = args      # قائمة قيم، مثل ["أحمد", "سعيد"]

class Rule:
    def __init__(self, head_name, head_args, body):
        self.head_name = head_name     # "جد"
        self.head_args = head_args     # [?X, ?Z]
        self.body = body               # قائمة من الأهداف Goals

class Goal:
    def __init__(self, name, args):
        self.name = name      # مثل "أب" أو "جد"
        self.args = args      # قائمة قيم أو متغيرات
كما نحتاج بنية بسيطة تمثل استعلامًا واحدًا (أو أكثر)؛ يمكن إعادة استخدام Goal:

python نسخ
class Query:
    def __init__(self, goals):
        self.goals = goals    # قائمة من الأهداف نريد تحقيقها
3. فكرة الـ Lexer/Parser لهذه اللغة
يمكنك استخدام نفس مبادئ الفصل الرابع:

تقسيم النص داخل كتلة منطق { ... } إلى رموز (Tokens):
كلمات مفتاحية: حقيقة, قاعدة, استعلام, منطق.

معرفات: أسماء العلاقات (أب, جد).

متغيرات: تبدأ بـ ?.

رموز: (, ), ,, ., :-.

تحويل كل سطر/جملة إلى عقدة مناسبة:
حقيقة ... . → كائن Fact
قاعدة ... :- ... . → كائن Rule
استعلام ... . → كائن Query
في تطبيق تعليمي أول، يمكن تبسيط parser جدًّا عبر التعامل «سطرًا بسطر» داخل الكتلة، مع بعض الدوال المساعدة لتقسيم النص.

4. محرّك الاستنتاج (Inference Engine) – الفكرة الأساسية
هدفنا: عند وجود قائمة من facts وrules واستعلام query، نريد إيجاد قيم للمتغيرات تجعل كل الأهداف في الاستعلام صحيحة.

نموذج عمل مبسّط:

نعرّف دالة solve(goals, env) حيث:
goals: قائمة أهداف متبقية نريد تحقيقها.

env: بيئة تربط المتغيرات بقيم (مثلاً: { "?X": "أحمد" }).

إذا كانت goals فارغة → نجحنا، ونطبع/نعيد البيئة env كحل.

وإلا نأخذ الهدف الأول g من goals ونحاول تحقيقه عبر:
أي حقيقة Fact مناسبة.

أو أي قاعدة Rule يمكن أن تنطبق.

التحقيق عبر حقيقة:

إذا كان g.name == fact.name وعدد الوسائط متساوٍ، نحاول توحيد (Unify) وسائط الهدف مع وسائط الحقيقة، وتحديث env إذا نجحت.

التحقيق عبر قاعدة:

نحاول توحيد رأس القاعدة مع هدفنا g، وإذا نجحت، نستبدل g بأهداف جسم القاعدة (body) ونتابع الحل لبقية الأهداف.

هذه الفكرة هي قلب لغات المنطق.

5. خوارزمية توحيد بسيطة (Unification)
التوحيد يحاول جعل قائمتين من الوسائط متطابقتين عبر إسناد قيم للمتغيرات.

إذا كان الوسيط ثابتًا (نصًّا) في كلا الجانبين، يجب أن يكونا متساويين.

إذا كان أحدهما متغيرًا (يبدأ بـ ?) والآخر ثابتًا:
إن لم يُسند المتغير بعد → نضيفه إلى env.

إن كان مسندًا → نتحقق أن القيمة نفسها.

يمكن تمثيل ذلك بدالة مثل:

python نسخ
def unify(arg1, arg2, env):
    # ترجع env جديدة إذا نجح التوحيد، أو None إذا فشل
    ...

في هذا الكتاب نركز على الفكرة، لا على كل تفاصيل التنفيذ؛ يمكنك الرجوع إلى مراجع Prolog لاحقًا لتطوير محرّك أكثر قوة.

6. ماذا تعلّمت من هذه اللغة المنطقية المصغّرة؟
كيف تصمّم بناء جملة بسيطًا للمنطق باستخدام مفاهيم عربية (حقيقة, قاعدة, استعلام).

كيف تفصل بين تمثيل المعرفة (حقائق/قواعد) وبين محرك الاستنتاج الذي يبحث عن حلول.

كيف تتكرّر نفس الأنماط التي رأيتها في «بسيطة»:
تصميم syntax
نموذج بيانات داخلي (AST مبسّط)
مرحلة تنفيذ/استنتاج
بهذه النواة يمكنك لاحقًا بناء لغات منطقية أكثر تعقيدًا، أو فهم ما تفعله أجزاء المنطق في لغات مثل البيان على مستوى مبسّط وواضح.

7. تمارين واقتراحات للتجربة
كتابة قاعدة جديدة
أضف حقائق جديدة مثلًا عن علاقة أم، ثم عرّف قاعدة جدة(?X, ?Z) تشبه جد لكن تستخدم أم بدل أب. فكّر كيف ستتغير خوارزمية الاستنتاج (غالبًا لن تحتاج لتغيير كبير، بل مجرد إضافة حقائق وقاعدة جديدة).

استعلامات مختلفة على نفس القواعد
بعد تعريف أب وجد، جرّب استعلامات متنوعة:

استعلام أب("أحمد", ?ابن).

استعلام أب(?أب، "ليلى").

استعلام جد(?جد، ?حفيد).

راقب كيف تتغيّر النتائج، وكيف تعبّر البيئة env عن الحلول.

تغيير شكل بناء الجملة (اختياري)
جرّب تخيّل شكل آخر للبناء (Syntax)، مثل:

text نسخ
حقيقة: أب("أحمد", "سعيد").

قاعدة: جد(?X, ?Z) إذا أب(?X, ?Y) و أب(?Y, ?Z).

واسأل نفسك:

أي الشكلين أوضح لك كمبرمج عربي؟
ما الذي سيتغيّر في الـ Lexer/Parser إذا اعتمدت الشكل الجديد؟
هذه التمارين هدفها أن ترى أن لغة المنطق ليست «سحرًا»؛ بل هي تطبيق منظم لأفكار: تمثيل المعرفة، والتوحيد، والبحث عن حلول عبر قواعد.

الفصل التاسع: خاتمة ونصائح للاستمرار
بهذا الفصل نصل إلى نهاية هذا الكتاب، لكنه ليس نهاية رحلتك مع بناء اللغات، بل بداية مرحلة جديدة تعتمد فيها أكثر على نفسك وتجاربك.

في الصفحات السابقة انتقلت معنا من:

فكرة لغة تعليمية صغيرة («بسيطة»)
إلى مفسِّر يعمل بالأسطر، ثم مفسِّر يدعم الكتل والشروط والحلقات
ثم إلى بنية أكثر تنظيمًا (Lexer / Parser / AST)
ثم توسعة اللغة بالأنواع والدوال ورسائل الخطأ
ثم تنظيم كل ذلك في مشروع صغير يمكن تشغيله
ثم نظرة على تصميم بناء الجملة للغات عربية
وأخيرًا، نواة لغة منطق عربية مصغّرة
هذه ليست دورة أكاديمية كاملة في نظريات اللغات، لكنها خريطة عملية تعطيك مسارًا واضحًا: من نص بسيط إلى مترجم صغير.

1. ماذا يجب أن تكون قد اكتسبته الآن؟
إذا قرأت الفصول بترتيبها وجربت على الأقل بعض التمارين، فمن المفترض أنك أصبحت:

تفهم المراحل الأساسية لبناء لغة:
نص → تحليل أولي (أسطر أو Tokens)
Tokens → بنية داخلية (AST أو ما يشبهها)
بنية داخلية → تنفيذ أو استنتاج
غير خائف من لمس مفسِّر مكتوب بلغة مثل Python وتعديله.

أكثر وعيًا بالتحديات الخاصة باللغات العربية (بناء الجملة، الخلط بين العربي واللاتيني، الأرقام والرموز...).

قادرًا على قراءة أكواد مفتوحة المصدر للغات صغيرة وفهم الفكرة العامة منها.

إذا شعرت أن بعض هذه النقاط ما زال غير واضح، فذلك طبيعي؛ يمكنك العودة إلى الفصول التي أحسست معها بالسرعة أو القفز وإعادة قراءتها مع تنفيذ التمارين.

2. كيف تتابع بعد هذا الكتاب؟
أ) تنفيذ «بسيطة» كاملة بنفسك
أنشئ مجلد مشروع جديدًا.

انسخ الأفكار الأساسية من الفصول 2–6، لكن أعد كتابة الكود بنفسك دون نسخ حرفي.

أضف لمستك الخاصة على اللغة:
اسم مختلف.

كلمات عربية أخرى.

نوع جديد من الأوامر (مثلاً: قراءة إدخال من المستخدم).

الفكرة هنا أن تنتقل من قارئ/منفّذ للأمثلة إلى مؤلف لمشروع صغير.

ب) بناء DSL صغيرة لمجال تهتم به
اختر مجالًا تحبّه:

وصف سيناريوهات اختبار.

تعريف قواعد عمل (Business Rules).

وصف سيناريوهات قصصية، أو حوارات لعبة، أو تدفّقات روبوت محادثة.

حاول أن تصمّم لغة مجالية (DSL) بسيطة لهذا المجال:

حدّد الكلمات الأساسية.

صمّم بناء جملة بسيطًا وواضحًا.

اكتب مفسِّرًا صغيرًا ينفّذ هذه الأوامر.

ج) التعمّق في اللغات والمنطق والبيان
إذا راق لك الجزء المنطقي والحديث عن البيان، يمكنك لاحقًا:

قراءة مراجع مبسّطة عن Prolog ولغات المنطق.

الاطلاع على مصادر تتحدث عن تصميم اللغات (Language Design، Compiler Construction).

3. نصائح عامة لمن يكمل طريق بناء اللغات
ابدأ صغيرًا دائمًا
لا تحاول أن تبني لغة عامة تنافس اللغات الكبرى من المحاولة الأولى؛ ابدأ بنواة بسيطة جدًّا، ثم أضف قدرات قليلة في كل مرحلة.

افصل بين المراحل بوضوح
حاول أن تحافظ على الفصل بين:

القراءة والتقسيم (Lexing)
التركيب (Parsing)
التنفيذ أو الاستنتاج (Interpreter / Engine)
هذا يجعل التطوير أسهل، ويقلّل من الأخطاء.

اكتب أمثلة واختبارات
حتى لو لم تستخدم إطار اختبار رسمي، احفظ دائمًا ملفات أمثلة صغيرة:

كلما أضفت ميزة للغة، أضف مثالاً يختبرها.

شغّل هذه الأمثلة في كل مرة تغيّر فيها جزءًا أساسيًا من المفسّر.

انتبه للغة العربية، لكن لا تجعلها عائقًا
الكتاب شجّعك على استخدام كلمات عربية وتعريب بناء الجملة، لكن يمكنك دائمًا:

مزج العربي بالإنجليزي عندما يكون ذلك أبسط.

البدء ببناء جملة قريبة من لغات شائعة ثم تعريبها تدريجيًّا.

اقرأ لغات الآخرين
ابحث عن لغات صغيرة مكتوبة كهوايات (Toy Languages) واقرأ مفسّراتها ومترجماتها؛ ستجد أن نفس الأنماط تتكرر، وستتعرّف على حلول مختلفة لنفس المشكلات.

4. كلمة أخيرة للقارئ
إذا وصلت إلى هنا، فهذا يعني أنك قضيت وقتًا مع فكرة كانت في السابق تبدو
"غامضة" أو "بعيدة"؛ فكرة أن تبني لغة برمجة بنفسك.

لا تحتاج إلى إذن من أحد لتجرّب بناء لغة صغيرة، ولا إلى لجنة علمية لتمنحك لقبًا معينًا؛ كل ما تحتاجه هو:

فضول حقيقي.

استعداد لتجربة أشياء قد تفشل أول مرة.

وهدوء في قراءة رسائل الخطأ وتتبع مصدرها.

أتمنى أن يكون هذا الكتاب قد جعل الطريق أوضح وألطف، وأن يكون
جسرًا صغيرًا بين حبّك للبرمجة وبين عالم تصميم اللغات وبناء المفسّرات والمترجمات.
